Every step a claim passes through, from the intake form to a paid or denied outcome — what runs it, and exactly where Camunda's job ends and yours begins.

Phase 01 Intake
01

Submit claim

Claimant fills out the claim form and attaches evidence — photos, a police report, receipts.

React / Next.jsfile upload widget
Global

Camunda renders nothing here. No customer-facing UI ships with the platform, ever.

02

Receive & store

Backend accepts the submission, uploads files to object storage, and writes the claim record.

Node/Express or Spring BootPostgreSQLS3
Global

Camunda holds no business data and no files — only its own orchestration state.

03

Start the process

Backend calls Zeebe to spin up a process instance keyed to this claim's ID.

Zeebe client (gRPC/REST)
Native

This is the engine's actual job — sequencing the claim begins right here.

Phase 02 Automated processing
04

Validate claim

A worker checks required fields are present and confirms the policy is active.

job worker (Node/Java)policy service
Global

Camunda delivers the job to a worker — it never computes the result itself.

05

Route the claim

Low-complexity, low-value claims go straight through; everything else waits for a person.

DMN decision table
Native

DMN tables ship with the engine — simple rule evaluation is what Camunda is built for.

Actuarial math beyond a rule table → app-specific gap
06

Read the evidence

Uploaded documents and photos are extracted into structured claim data.

worker (Python/Node)Claude API
Global

No OCR or document intelligence exists anywhere in the platform.

07

Score the risk

The claim is checked against history and known patterns for fraud signals.

workerClaude API reasoningclaims-history store
Global

No modeling, scoring, or inference capability of any kind.

Phase 03 Human review
08

Route by risk

High-risk or high-value claims are pulled aside specifically for a person to look at.

exclusive gateway
Native

Branching on a variable is core engine behavior.

09

Adjuster reviews

A person opens the claim, reads the AI summary and risk score, and makes the call.

Camunda Tasklistor custom UI via Task API
App-specific

Camunda ships the task queue; the reviewer's actual working surface is generic and plain — a real adjuster tool needs its own frontend.

Phase 04 Resolution
10

Route the decision

Approve, deny, or send the claim back for more information.

exclusive gateway
Native

Another branch on the adjuster's decision variable.

11

Pay out, if approved

A disbursement is triggered for the approved amount.

workerStripe / ACH / disbursement API
Global

Camunda doesn't move money, ever.

12

Draft denial, if denied

A denial letter is generated citing the specific coverage reason.

workerClaude API draftingPDF generation
Global

No document generation exists in the platform.

13

Notify the claimant

The outcome — either direction — is sent to the customer.

workerSendGrid / Twilio
Global

No delivery channel of any kind ships with Camunda.

Phase 05 Close
14

Close the case

A worker writes the final status to the claims database as the engine ends the instance.

workerPostgreSQL
NativeGlobal

Split: ending its own process instance is native behavior; writing the durable business record is not the engine's job.

15

Check status

The claimant checks progress; operations watches the pipeline for stuck claims.

frontend polling backendCamunda Operate (internal)
App-specific

Operate covers process health for your team, not a customer status page or regulatory reporting — how much of that you need depends on the insurer.

Fifteen steps, three that Camunda runs itself, one split down the middle, eleven built entirely around it. That ratio is normal — the engine's job is staying small.
